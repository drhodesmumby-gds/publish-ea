    Building Control

    The technical architecture supporting the enforcement of building regulations, structural safety, and on-site compliance inspections.

    Unlike Development Management, Building Control is rarely public-facing. It is a highly technical, field-centric service. Its architecture must prioritize offline-capable mobile applications for site inspectors, and rigid, immutable audit trails to comply with the Building Safety Act and the Building Safety Regulator (BSR).

    Note: Customer is used to describe the users of this service, as building control functions compete with the private sector for some of their work.

    Business process

    This section outlines the business process at each phase of a building control application. Expand each phase to compare the baseline legacy architecture against modern target states.

    1 Submission

    • Business Process
    • Anti-patterns
    • Target Architecture

    The process: Builders, architects, or homeowners submit technical structural drawings before work commences. The key architectural challenge here is securely handling massive file sizes (e.g. 500MB CAD files).

    Required LGAM Taxonomy Nodes:

    CapabilitiesForms DataDocument and records management CapabilitiesPayments
    Anti-pattern: Disconnected large file transfer

    Because standard council web forms limit file sizes (e.g., to 10MB), applicants email links via external file-sharing services for their massive CAD files. Officers manually download these and store them on unmanaged local network drives, breaking the audit trail.

    Best Practice: Unified blob storage and pre-signed URLs

    Modern submission portals utilize cloud-native object storage. When a user needs to upload a massive BIM model, the frontend requests a temporary, pre-signed URL from the API Gateway, allowing the user's browser to stream the file directly into the council's secure cloud storage, bypassing the web server's memory limits.

    Real-world impact
    • Information Governance

      Eliminates "Shadow IT" (staff using personal file-sharing accounts). Highly sensitive structural drawings (e.g., for banks or schools) are stored in encrypted, auditable enterprise environments.

    • System Performance

      Prevents massive file uploads from crashing the primary web forms server, ensuring high availability for other citizens trying to access council services.

    2 Validation

    • Business Process
    • Anti-patterns
    • Target Architecture

    The process: Local authority staff must ensure that the correct type of application has been made and that an appropriate payment has been received. Depending on the type of works, a bespoke quote will be made and payment taken.

    Required LGAM Taxonomy Nodes:

    ChannelsEmail CapabilitiesPayments DataGeospatial data
    Anti-pattern: Geospatial checks after submission

    Dependent on location and types of work, certain types of check are restricted. Currently these checks only happen after submission, meaning delays for customers.

    Best Practice: Integrated spatial checks at submission

    Using a rules-as-code submission platform that integrates with available geospatial information means that the correct application type can be made first time, reducing errors and delays.

    Real-world impact
    • Increased sustainability

      Providing a better customer experience will increase repeat business and improve the sustainability of council services in a competitive market.

    • Faster processing

      By automating checks in the submission process there is less time taken to validate applications, reducing processing times and decreasing the burden on staff.

    3 Design check

    • Business Process
    • Anti-patterns
    • Target Architecture

    The process: Building Control surveyors must thoroughly review complex structural plans and calculations against national Building Regulations (e.g. fire safety, thermal performance, escape routes) before any construction work is permitted to begin.

    Required LGAM Taxonomy Nodes:

    DataDocument and records management CapabilitiesWorkflow CapabilitiesBusiness rule engines
    Anti-pattern: Flattening 3D BIM to 2D PDFs

    Architects design modern buildings using rich, data-heavy 3D Building Information Models (BIM). However, current council systems force applicants to "flatten" these models into hundreds of static 2D PDF blueprints for submission. Surveyors then spend hours manually measuring distances on screen, losing all the embedded structural metadata.

    Best Practice: Automated BIM Interrogation

    Modern architectures accept native BIM formats (such as IFC). Instead of manual measurement, the compliance engine automatically runs rule-sets against the model's spatial metadata—for example, instantly calculating if the distance between any desk and a fire exit exceeds the maximum allowed by regulations, flagging only the failures for the human surveyor to review.

    Real-world impact
    • Regulatory Accuracy

      Completely removes human error from complex geometric calculations, ensuring higher building safety standards.

    • Accelerated Approvals

      Reduces the plan checking time from weeks down to days by automating the bulk of the compliance math, allowing highly-trained surveyors to focus purely on exceptions.

    4 Site inspections

    • Business Process
    • Anti-patterns
    • Target Architecture

    The process: The core of Building Control. Surveyors travel to active construction sites to inspect foundations, damp proofing, and steelwork. They must record evidence (photos, notes, pass/fail status) and link it precisely to the property record.

    Required LGAM Taxonomy Nodes:

    InterfacesMobile working DataGeospatial data
    Anti-pattern: "Online-only" web apps in the field

    Deploying standard council web-portals to tablets. When inspectors go into concrete basements or rural development sites without 4G, the application drops the session, forcing them to use pen-and-paper and transcribe notes back at the office.

    Best Practice: Offline-first Mobile Architecture

    Target architectures utilize native or PWA (Progressive Web App) mobile technologies designed as "offline-first". Inspectors download their daily case lists and mapping tiles to a local encrypted SQLite database on the device via Wi-Fi in the morning. They log data seamlessly without signal; the app's sync-engine automatically handles the API payload delivery to the back-office once 4G is restored.

    Real-world impact
    • Operational Efficiency

      Recovers up to an hour per inspector, per day, by eliminating the need to return to the office to manually upload photographs from a digital camera and type up paper notes.

    • Data Quality & Compliance

      Photographic evidence is automatically tagged with GPS coordinates and timestamps at the exact moment of capture, creating an unassailable legal audit trail.

    5 Certifications and Notices

    • Business Process
    • Anti-patterns
    • Target Architecture

    The process: Following satisfactory inspections, the council issues a formal Completion Certificates.

    Required LGAM Taxonomy Nodes:

    DataData quality and governance
    Anti-pattern: Non-public registers

    Building Control information that is not publicly accessible means that interested parties in a property are more reliant on paid for conveyancing services. This slows down the housing market and inhibits labour markets flexibility.

    Best Practice: Public registers of Building Control information

    Providing publicly accessible records supports a greater degree of self-service and provides the basis for better integration of building control information into other systems such as Section 106 monitoring.

    Real-world impact
    • Increase planning obligation compliance

      Linking completions of sites to the planning obligations which exist there helps proactive monitoring and increases the percentage of revenue collected with less spend on manual monitoring activities.

    6 Reporting KPIs

    • Business Process
    • Anti-patterns
    • Target Architecture

    The process: Post-Grenfell legislation requires stringent, ongoing data sharing regarding High-Risk Buildings (HRBs) with the central Building Safety Regulator (BSR).

    Required LGAM Taxonomy Nodes:

    IntegrationPartner (B2B) integration DataData quality and governance
    Anti-pattern: "Swivel-chair" regulatory reporting

    Building Control officers must manually run reports in their local system, export them to Excel, and manually upload them to a central government portal. This creates a lag in safety data and a high risk of transcription errors regarding critical structural information.

    Best Practice: B2B API integrations and immutable logs

    Target architectures automate statutory compliance. When an inspector signs off a High-Risk Building phase, the workflow engine automatically triggers a webhook. The API Gateway formats the required payload (anchored by the UPRN) and pushes it synchronously to the Building Safety Regulator's APIs.

    Real-world impact
    • Regulatory Compliance

      Ensures absolute, real-time compliance with the Building Safety Act without manual overhead. Central regulators have immediate visibility of high-risk site statuses.

    • Liability Reduction

      Immutable, system-to-system data transfers prevent human error in safety reporting, securing the "golden thread" of building information and reducing the council's legal risk exposure.

    Target data models

    There are not yet published data standards for storing and sharing building control information. However, these are currently being developed, and thinking about how you could align to them over time will help you share information with partners in both central and local government.

    What makes building control technically different

    Every council domain has integration points with shared capabilities. Building control is architecturally distinctive in several ways that affect how you design those integrations:

    The work happens on site as well as at a desk

    Surveyors spend much of their time inspecting live construction sites, often in basements, rural areas or partly built structures with no reliable signal. Device security policies and unreliable mobile apps mean many surveyors copy drawings to personal cloud storage before leaving the office. This means:

    • Field tools must work offline and sync back to the case record when a connection returns, without creating duplicate or conflicting records.
    • Approved plans and case history must be available on the device through the official system, not copied to local or personal storage.
    • Site photos and notes need to be date-stamped, geotagged and linked to a specific visit as they are captured, because they may later be used as evidence in enforcement or prosecution.
    • On large developments a surveyor may inspect the same element on many identical plots in one visit, so observations need to be recorded once and applied to several plots.

    A competitive, fee-earning service with bespoke pricing

    Unlike most council services, local authority building control competes directly with private RBCAs. It must recover its costs from fees while still funding non-chargeable statutory work such as enforcement and dangerous structures. A significant proportion of fees are quoted case by case rather than taken from a fixed schedule. This means:

    • Payment integration must support both payment at submission and a submit-now, pay-later route once a bespoke quote has been agreed.
    • Time spent on each case needs to be captured, ideally without manual timesheets, so that fees can be set with confidence and compared with the work actually done.
    • Customer experience is a commercial concern. Householders often leave the choice of provider to their builder or architect, so builders and agents who cannot see progress or book inspections easily may move their next job to a private provider.

    Data arrives from other organisations, mostly as documents

    Local authorities remain the statutory backstop and keep the public register, so they receive data from organisations outside the council. Initial Notices from RBCAs and CPS notifications (for example from Gas Safe) are generated from structured systems, then sent as PDFs or file attachments and re-keyed by hand. This means:

    • Inbound integration needs shared data standards and validation at source, not just a mailbox, so that notices can be read and routed automatically.
    • Notices feed the statutory public register, so errors made when re-keying them end up in the public record.
    • Property identification is a constant source of friction: missing or wrong UPRNs, new developments without official addresses, and notices sent to the wrong authority. UPRN validation should happen before submission.
    • The relationship continues through the whole project, including amendments, extensions of time, cancellations, reversions to the local authority and final certificates, so standards must cover the lifecycle, not just the first notice.
    • Most back-office products are closed and offer no APIs, so exchanging data with RBCAs, the BSR or other council services usually depends on what the supplier chooses to expose.

    Non-chargeable statutory work: dangerous structures and enforcement

    Local authorities are the statutory backstop for building safety. They must respond to reports of dangerous structures, often urgently and outside normal hours, and enforce breaches of the Building Regulations, including on work that reverts from RBCAs. Neither is funded by fees, and both draw on the same surveyors as fee-earning work. This means:

    • Dangerous structures need their own reporting route for the public and partners such as the fire service, with urgent triage and out-of-hours allocation, separate from planned inspections.
    • Enforcement can end in prosecution, so site evidence, notices and correspondence must be complete, timestamped and tamper evident, able to stand up in court.
    • Time spent on non-chargeable work should be recorded separately from fee-earning work, so that it is visible in reporting and can be set against cost recovery.
    • These cases often start with no existing application, so the system must be able to create a case from a property or location alone.

    Regulatory reporting and the golden thread

    Since the Building Safety Act, building control sits under national oversight from the Building Safety Regulator. Local authorities report performance data to the BSR each quarter using a prescribed spreadsheet, and the golden thread requires information about higher-risk buildings to be digital, secure and auditable throughout their life. This means:

    • KPIs should be generated from case data as a by-product of the work, not rebuilt by hand each quarter from separate trackers.
    • Every action (emails sent, requirements raised, inspections recorded) needs an automatic audit trail. Staff currently duplicate entries up to three times to prove that something was done.
    • Records must remain authoritative for the life of the building, not just the life of the case, which affects retention and records management.
    • New duties such as the Building Safety Levy add further reporting and monitoring dependencies that systems will need to support.
